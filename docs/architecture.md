# Architecture decisions

## Product boundary

Kids Guide answers “What can I do today with my child?” for children aged 12–95 months. A teacher shares a published activity; guardians continue it at home. Completion records reflect shared moments, not developmental scores or diagnoses. Turkish and English cover the interface and curated content; teacher-written messages remain in their original language.

## Application and data

Expo Router screens call a typed `KidsGuideGateway` through TanStack Query. `AppProvider` selects the offline implementation or Supabase implementation. Zod validates incoming data. Screens do not manage authentication tokens or database queries.

| Mode | Persistence | Authentication |
| --- | --- | --- |
| Offline demo | Device/browser AsyncStorage | Fictional parent/teacher selector |
| Online | Supabase PostgreSQL | Supabase Auth |

Startup mode and project settings come from `apps/mobile/appsettings.json`. The current default is online. In-app mode switches last for the session and clear cached account context. They do not upload demo data or synchronize offline edits. Supabase initialization is lazy, so starting in offline mode does not initialize cloud authentication. Token refresh is on demand.

Native sessions use SecureStore with bounded chunks for large tokens; browser sessions use localStorage. Startup checks the saved session before displaying welcome or the main app. Passwords are never persisted by the application. Public connection settings are bundled into the app; a new APK is needed to change them. A different Supabase project has independent users and data.

The opening illustration leads to login with signup and offline-demo options, or directly to the area hub when a session is restored. Signup supplies only display-name metadata; database relationships still control teacher access. When Supabase requires email verification, users confirm the email link and return to log in. A signup response without a session never opens the main app. Google login and automatic email-link callbacks are not implemented yet.

The area hub separates My child and My class. Each has its own navigation. Classroom posts retain their activity IDs when opening home activities, and completion preserves the return destination. Additional classroom tools from the V24.3.5 design are explicitly offline prototypes; see [integration decisions](v24-integration.md).

## Authorization

Parent and teacher are relationships rather than mutually exclusive global roles. Guardians link to children; teachers link to classes; enrollments connect children with classes. Publishing content is a separate administrator-assigned permission.

Supabase enforces access with PostgreSQL RLS, column grants, and scoped SQL functions. The client cannot assign memberships or trust user-controlled metadata to grant publishing permissions. Trusted administration provisions those relationships. Database migrations and seed data are versioned with the app.

Client-generated operation IDs make retries idempotent while allowing genuinely repeated activities. Age and search filters run before pagination. Writes validate membership, content references, age ranges, and complete bilingual published content.

## Scope

There is no custom API service, microservice infrastructure, or separate database server to operate. The native Android project is generated by Expo when needed and excluded from Git. The committed Expo config and locked dependencies are its inputs.

Pilot users and content/class administration currently use Supabase's trusted dashboard/SQL tools. The prototype has no management UI, public signup/recovery, invitations, media, notifications, real-account offline synchronization, or AI. These require explicit future work. Indexes and pagination support efficient access, but production load has not been benchmarked.
